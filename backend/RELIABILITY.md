# 2026-11-22 可靠性修复

## 已实现

- 事件接口在同一数据库事务中提交事件、决策、案件和建案审计，提交成功后才返回成功。数据库失败返回 503，调用方必须保留原事件并用相同业务键重试。
- SQL 是在线决策事实源。事务锁定 DecisionGuard 单行后读取已提交事件，计算窗口和历史图谱，再提交事件、决策、案件、审计与 EventProjection 任务。幂等判断查询 SQL，唯一索引兜底，不依赖 Redis 成功缓存或租约。
- 同设备、IP、地址账号数按事件时间过滤并去重。事件时间统一到幂等键中的毫秒，避免 MySQL 默认 DATETIME 丢失小数秒影响历史计算。
- 在线接口支持对已保留 SQL 历史的迟到补录，不再受 Redis 一小时水位限制。迟到事件在同一事务重算其后（含同时间）决策，使用原规则、阈值及名单快照；必要时补建案件，记录修正前后内容。原始返回保存在 EventProjection.original，回溯接口提供 original 和 corrections。重复请求返回当前修正结果，不再次计数。
- 提交前不写 Redis 或 Neo4j。提交后投影；失败任务保留在 SQL，后台每 5 秒重试，重启后继续，调用方无需重发已成功的事件。Redis 按 event_key 去重，图谱 MERGE 幂等。投影失败不影响基于 SQL 的后续决策。
- 规则新增、修改、停用、删除同时更新知识文档；事务提交后刷新规则缓存。检索直接读取知识表，避免进程内检索缓存过期。
- 仿真使用历史决策的特征及名单快照，不读取当前图谱和名单。它比较固定历史输入下的规则差异，不模拟策略反馈，也不修正旧快照中的特征错误。

## 尚未达到的边界

- 这是 SQL 事务加持久化投影任务，不是跨存储分布式事务。外部图谱展示可能暂时滞后；持续故障会积压任务。已经成功投影后外部存储自身丢数据，需要从 SQL 重建，当前不自动检测这种丢失。
- SQL 提交失败的事件没有被接纳，返回 503；上游仍须重试。但它不再留下 Redis/图谱孤立写入。
- 旧版决策没有保存完整历史规则，无法精确重算；记录 decision.recompute_required 审计项，需人工核对。不得套用当前规则冒充历史规则。已处置案件不自动撤回业务动作；保留处置状态并记录人工复核审计。
- 当前以全局 SQL 行锁串行决策、扫描历史并重建内存图；用于演示规模，吞吐和延迟未完成压测。扩容需实体分区锁、增量物化特征及异步重算。
- 规则运行时仍是单进程缓存，多实例广播失效和审计链并发串行化未在本次实现。
- RAG 仍使用 BM25，没有完成向量检索或云模型联调。历史案件的决策快照与当前规则知识可能有版本差异，不能把当前规则当作历史决策依据。
- 本次只更新代码与验证，不代表已更新运行中的服务或完成生产验收。
