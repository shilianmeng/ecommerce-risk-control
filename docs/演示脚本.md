# 电商风控 · 5 分钟演示脚本

> 目标：让面试官在 5 分钟里看到四件事——实时决策能解释、团伙能被图谱抓出来、策略改动先仿真再上线、操作留痕不可篡改。
>
> 文中标「演练结果」的数字，是在隔离沙箱（临时 SQLite + fakeredis + 内存图，跑的是同一套代码和演示数据）里实际跑出来的。真库 2026-11-25 按当时时间重灌过，决策数、案件数和沙箱一致；时间相关的数字（如「近 1 天」）以页面为准。第④步的仿真数字是在真库上实测的：46 个案件都已按证据处置，黑名单 20 条，审计链 157 条。

## 演示前检查（1 分钟，面试前做）

1. `powershell -File scripts\start_infra.ps1`，再起后端（`backend\python run.py`）和前端（5181）。或 VS Code F5「电商风控（后端 + 前端）」。
2. 打开 http://127.0.0.1:8092/health，确认 `"redis": true, "graph": "neo4j"`。
3. 开两个浏览器窗口：一个登 `strategist`，一个登 `auditor`（密码都是 123456）。admin 也行，但分角色演示更能体现权限。
4. 演示数据的时间以灌入时刻为准，往前铺 3 天左右。离面试太久的话，大盘「近 1 天 / 近 7 天」会变空，可以先备份库再重灌（方法见 README「数据说明」）。
5. **注意：第 ②④ 步会往正式库 `RiskControl` 写数据**（新事件、案件处置、黑名单），是真实操作，不可撤回。正式面试前要排练的话，先备份库再练。

## ① 态势大盘（30 秒）· `/dashboard`

**操作**：时间段选「近 30 天」。

**讲**：
- "这是风控的全局视图。367 条决策里拒绝 41 条、人审 5 条，拦截率约 12%。"
- 指着规则命中排行："命中最多的是 R-003 团伙关联和 R-002 同设备多账号领券，说明这批数据里羊毛党是主要风险。"
- 切到「近 1 天」："时间段可切。哪个时间段没有数据，页面会明确提示，不会只给一片空白。"

> 演示数据是场景脚本生成的**原始事件**，但每一条都走真实决策链路算出来——特征、图谱、案件、审计都是系统算的，不是往结果表里插的。被问到就这么答。

## ② 实时决策 + 可解释（90 秒）· `/simulator` → `/decisions`

**操作 A：黄牛下单**
1. 事件类型选「下单」，金额改成 **3999**，注册天数保持 3。
2. 点「连发 6 次（换订单号/时间）」。

**演练结果**：前 5 次 `PASS 25`（只命中 R-006 新账号大额订单），第 6 次 `REVIEW 70`（R-004 同设备 1 小时下单超过 5 次 + R-006）。

**讲**：
- "同一台设备，第 6 单的时候滑动窗口计数到了 6，触发 R-004。窗口用 Redis ZSET 按事件时间统计，不是固定窗口计数器，所以不会在整点边界清零。"
- "25 + 45 = 70，落在 60–79 的人审区间，自动建了案件。"

**操作 B：幂等**
3. 点「重放上一次（验证幂等）」。

**演练结果**：返回 `duplicate: true`，分数不变，事件数不增加。

**讲**："业务系统超时重试很常见。幂等键是订单号 + 事件类型 + 毫秒时间戳，数据库唯一索引兜底，重放不会被重复计数。"

**操作 C：看回溯**
4. 去「决策回溯」，点刚才那条 REVIEW。

**讲**：
- "每条命中规则都展开到原子条件：`device_order_count_1h` 实际值 6、阈值 > 5、成立。审核员不用猜系统为什么拦。"
- "特征快照和规则版本号也存下来了，以后规则改了，这条决策依然能按当时的口径解释。"

> 备选（恶意退款）：事件类型选「售后申请」，原因「未收到货」，金额 2399，**换一个新账号**后连点「发送 1 次」4 次。演练结果：前 2 次 `PASS 20`（R-011），第 3 次起 `REJECT 80`（R-008 + R-011）。

## ③ 关联图谱抓团伙（60 秒）· `/graph` → `/cases/:no`

**操作**：打开「关联图谱」，点 **G001**。

**讲**：
- "这是羊毛党团伙：12 个账号，共用一个 IP `223.104.18.77`、两台设备、三个地址。单看任何一个账号，领券次数都不算夸张；连起来看就是一伙人。"
- "图存在 Neo4j，账号和设备、IP、手机、地址是边，团伙就是连通分量。决策时还会算 2 跳内的关联账号数，喂给 R-003。"

**再打开一个案件**：「案件审核」里找账号 `r5000`（恶意退款）的案件，进详情。

**讲**：
- "一页里有账号画像（历史决策分布、历史案件）、特征快照、命中规则、2 跳关系图和审计记录。这个案件已经处置过了，处置备注里写着命中的规则和证据。"
- 在「RAG 审核辅助」卡片里点「生成审核建议」："它检索规则说明和判例，给出带引用编号的处置建议。"
  - 开了 8093（F5「电商风控 + 本地模型」，Qwen2.5-1.5B + 风控 LoRA）：返回大模型生成的建议，引用的规则和判例都在检索结果里。本机 4G 显卡一次约 28 秒，先点下去再讲别的。
  - 没开 8093："大模型不可用时自动降级成检索模式，审核流程不受影响。"

## ④ 处置闭环 + 规则仿真（60 秒）· `/cases` → `/namelists` → `/simulation`

库里原有的 46 个案件都已处置。现场处置用第②步黄牛下单新建的那个案件（账号是模拟器随机生成的 `demo_…`）。

**操作**（auditor 窗口）：
1. 「案件审核」里找第②步新建的待审案件，进详情，点「认领」；在处置区勾「拦截订单」「拉黑账号」，结论选「确认欺诈」，点「提交处置」。
2. 打开「名单管理」。

**结果**：黑名单里自动出现这个 `demo_…` 账号，原因写着「案件 … 处置」。原有的 20 条（16 个账号、4 台设备）是之前按证据处置 46 个案件时写入的。

**讲**："处置不是改个状态就完了：拉黑账号、封禁设备会直接写进名单，这个账号下一次请求在名单这一步就被拒，不用再算规则。认领和处置都是在接口返回之前就提交的，认领完马上处置不会读到旧状态。"

**操作**（strategist 窗口）：
3. 打开「规则仿真」，先直接点「开始仿真」，看基线。
4. 编号填 `R-012`，表达式改成 `device_account_count_24h >= 8`，分值 40，事件类型勾「登录」，再仿真。

**真库实测结果**（未算第②④步新增的数据）：
- 基线：367 条决策，已确认欺诈 46 个，现有规则全部抓到，召回 46/46。
- 把 R-012 从 ≥5 放宽到 ≥8：4 条决策从 REVIEW 70 变成 PASS 30（羊毛党 w2008–w2011 的登录），召回降到 42/46（91.3%）。
- 备选：把 R-003 表达式改成 `false`、分值 0（相当于停用），召回降到 58.7%。

**讲**：
- "策略师改规则前，先在历史决策的特征快照上回放：哪些决策会变、已确认的欺诈还能不能抓到、会不会误伤已确认正常的用户。仿真不读线上状态、不落库、不建案。"
- "这里放宽阈值少了 4 条人审，可这 4 个都是已确认的团伙成员，召回直接掉了 4 个，所以这个改动不该上线。"
- 被问误伤率为什么是空的："现在的标签全是确认欺诈，没有人工判为正常的案件，误伤率算不出来，我没为了填数去编结论。"

## ⑤ 审计防篡改（20 秒）· `/audit`

**操作**：点「校验哈希链完整性」。

**讲**："每条审计记录都带上一条的哈希，像一条链。刚才的处置、名单变更都在里面。改、删、插任何一条，从那条往后都对不上，校验会指出断在哪。"

## 常见追问（备答）

| 问 | 答要点 | 代码 |
|---|---|---|
| Redis / Neo4j 挂了怎么办？ | SQL 是事实源，决策只依赖 SQL 历史；Redis、Neo4j 是提交后的投影，失败留在 `eventprojection` 表，后台每 5 秒重试。补投逻辑有单元测试，也在真实环境里分别停掉 Redis、Neo4j 验证过：停服期间决策照常，恢复后自动补齐。 | `services/reliability.py`、`services/decision.py` |
| 客户端收到 200，数据一定写进库了吗？ | 以前不一定：FastAPI 带 yield 的依赖默认在响应发出后才跑 yield 后面的提交，认领完马上处置会读到旧状态报 409，提交失败客户端也已经收到成功。现在会话依赖设成 `scope="function"`，提交完才发响应；有测试在响应头发出那一刻另开会话读库验证。 | `db/session.py` 的 `DbSession` |
| 迟到事件怎么处理？ | 同一事务里重算它之后的决策，用当时的规则和阈值快照，修正前后都记审计。 | `reliability.repair_later` |
| 规则写错了怎么办？ | DSL 自己实现，不用 eval；保存前做静态类型检查，库里有坏规则启动时跳过并告警，不拖垮决策。 | `engine/dsl.py`、`services/runtime.py` |
| 吞吐多少？ | 如实说：现在是全局行锁串行 + 每次扫描历史，只适合演示规模，没压测。扩容方向是按实体分区加锁、增量物化特征。 | `decision.decide` 里的注释 |
| 数据是真的吗？ | 演示事件是场景脚本生成的原始事件（固定种子），但全部经过真实决策链路；没有真实电商数据。 | `services/bootstrap.py` |
| 为什么不用固定窗口计数？ | `INCR + EXPIRE` 在窗口边界清零，59:59 和 00:01 被拆开；ZSET 按事件时间 `ZCOUNT` 是真滑动。 | `engine/features.py` |
| 只看阈值和看反事实有什么区别？ | 阈值只说明条件成立；反事实把每个条件单独翻转再求值，OR 规则两支都成立时谁都不关键，这是看阈值看不出来的。决策层再逐条去掉命中规则重新仲裁，回答「去掉哪条结论就变」。案件详情「反事实」一栏可现场展示。 | `engine/dsl.counterfactual`、`engine/whatif.py` |

## 演示后

- 演示会在正式库留下新事件、已处置案件和黑名单记录，都是真实操作产生的。
- 服务不用时：关掉后端和前端窗口即可；Redis / Neo4j 是脱离启动的，需要时在任务管理器里结束 `redis-server.exe` 和 Neo4j 的 `java.exe`。
